# macOS 手动触发的一键更新

## 问题与方案

原实现中 macOS 的 `installAction` 是 `open-package`：下载 DMG 后只调用 `shell.openPath`，提示用户退出并拖入“应用程序”。这属于手动分发流程，缺少应用内自动安装步骤。

本次保留既有 GitHub 正式 Release 查询、下载与 SHA256 验证，不新增另一套更新服务，不在启动时联网检查或自动下载。Mac 用户下载完成后点击“安装并重启”，程序自动准备、替换 `.app` 并重新打开。

当前已发布的 0.1.11 没有这套新逻辑，首次升级到包含本修复的版本仍需按旧流程安装一次；后续版本才能通过新入口更新。没有改动已发布标签或资产。

## 文件与行为

- `app/release-updates.js`：Mac 下载继续选择当前架构 DMG，安装动作改为 `install-macos`；点击安装时复核文件大小和 SHA256，并向安装控制器传递同一份可信元数据。
- `app/mac-update-installer.js`：校验当前安装、以只读/不浏览方式挂载本次镜像，核对包内唯一应用的 Bundle ID、版本、Mach-O 架构和完整签名，拒绝包外链接。正式签名版本不接受不同 Team 或降级为 ad-hoc。复制到安装目录同盘暂存位置并再次验证，成功卸载本次镜像后才启动独立助手。
- `app/mac-update-worker.js`：只使用 Node 内置模块，复制到应用包外，由现有 Electron 的 Node 模式运行。完成助手握手后主程序才退出；助手等待旧 PID 结束，再将旧包改名备份、新包移动到原路径，随后请求系统重新打开。重命名或打开失败会回滚；未收到新宿主启动确认时保留两份应用并记录未确认状态，不能把 `open` 返回成功当作应用启动成功。
- `main.js`、`index.html`：沿用宿主主窗口受限的更新 IPC，增加准备中的提示及“安装并重启”。新主窗口 DOM 就绪时才写启动确认。Windows 安装与 Linux 定位下载目录流程继续保留。
- CI：四个平台加入专用测试；Mac 原生测试会生成临时签名应用及 DMG，验证挂载、复制、签名、实际 Electron 助手握手、同盘替换及确认，不替换真实安装或打开前台应用。

## 权限与恢复

只操作当前真实安装应用及同一父目录下本次创建的 `.sanrenjz-update-*` 事务目录，不修改用户数据、插件、配置、账号或运行资料。目录不可写时在主程序退出前报错；不申请或保存管理员密码、不绕过 Gatekeeper、不删除 quarantine 属性、不修改签名包内部资源。从 DMG 或 App Translocation 运行时要求先正常安装。

成功更新保留上一版本应用作为恢复材料，后续更新时尽力清理更旧且已结束的成功事务；失败事务不会被当作缓存删除。镜像卸载只针对本次 attach 返回且对应指定挂载点的设备，只有退出码 16 且错误为 Resource busy 才有限重试，卸载失败不能继续退出安装。

## 验证与限制

Windows 上执行专用安装事务与更新服务测试：26 项通过，1 项 Mac 原生测试按平台跳过。真实临时目录覆盖准备不改旧包、哈希篡改、复制失败、发布者变化、有限卸载重试、助手握手失败、重命名失败回滚、启动失败回滚、未确认启动保留备份、路径越界及用户数据保留。现有隐藏 Electron 更新界面与真实宿主 IPC 的 28 项检查通过；开发态和打包布局的模块导入检查通过。

Mac 原生测试仅在 darwin 运行，当前 Windows 环境跳过；因此源码测试不能代替 Intel/Apple Silicon 的原生挂载与签名验证，更不能代表用户 `/Applications` 实际权限和 Gatekeeper 交互已验收。需在正式发布前由两个 Mac runner 执行新增原生测试，并在用户设备验证首次迁移和后续升级。
